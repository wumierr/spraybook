## 3. 已实现能力与生产工作流(现状盘点)

**已实现**:现场计算(打药/吊运、地块/作业组/农户档案、用药类型库、工单覆盖层)→ 在线同步(幂等、离线队列、退避)→ 记账总表(原 Excel 12 列+增强列、搜索/月分页/客户过滤/CSV/列宽拖拽/行内编辑)→ 结算→账单→收款(FIFO 核销、余额转预收、经手人)→ 支出(七类、预支抵扣)→ 预收预支/分成 → 复式流水(借贷平衡断言、红冲不改性)→ 图表(echarts 本地化,12 组图,月/周/季/年)→ 报表 → Excel 历史导入(staging→行级复核→事务化落库+对账守恒)→ 主数据(客户/地块档案/药品只读)。

**生产动线(建议写进 README 首页)**:
日常现场:计算器算钱→工单"同步到账本"(现场有网)或"复制工单文本"(离线,见 §4 缺口)。
当晚/周末:账本里 工单→生成结算→确认;收款页按客户收钱;支出页记油费药费;总表看全局;图表看月度。
对账:流水页借贷全平 + 总表合计 vs 手账;月末 db:backup。

## 4. 计算⇄记账适配度(核心缺口)

- **在线同步链路**:字段匹配度高、幂等完善、队列健壮(探测门/退避/dead 上限)——唯一已打通通道。
- **离线通路 = 0**:计算器导出(JSON/文本,仅剪贴板无文件)→ 记账**无任何导入入口**;即使手工 POST /api/jobs 也会因导出 JSON **不含 result**、无 client_job_id 被拒。
- **导出勾选功能:不存在**(用户问"是否存在"——答案是整个功能未做,非实现不完整)。
- 计算器路径主行 unit_price 仍空(pricePerMu 只在 raw_json,P4 已知,本轮 GUI 实测再次确认)。
- 结构面:server 依赖图无环、计算核心零复制(快照式,合理);三套金额格式化语义不同(元/分)但无共享必要;ui.js 渲染层与 ledger app.js 零测试(UI 层可接受,冒烟靠 GUI)。

## 6. 方向判断(P6 的纲)

方向正确:数据流贴合"现场算钱→收钱→记账→对账"的真实作业;总表主界面+图表+Excel 化编辑符合用户工作习惯。**最大的产品级裂缝是"离线"**——主打离线场景(现场无网),但离线数据进不了账本,而修复成本不高(见 P6-M1)。其次是同步开不了(F1)让在线通路形同虚设,两者合起来意味着:计算器⇄记账的日常实际用法目前只剩 Excel 导入历史这一条单行道。
